# Reflexión sobre las prácticas de desarrollo de software seguro: Caso Artemis Financial

## Descripción del cliente y requisitos de software

Durante el proyecto trabajé con Artemis Financial, una empresa de consultoría financiera dedicada a desarrollar planes personalizados de inversión, ahorro y seguros para sus clientes. Al tratarse de una firma que administra información altamente sensible, como saldos bancarios, números de cuenta y estrategias patrimoniales, su principal necesidad consistía en modernizar sus operaciones digitales y asegurar la aplicación web y su API RESTful frente a amenazas externas. La empresa buscaba garantizar tanto la integridad de los datos estáticos como la confidencialidad de las comunicaciones entre el cliente y el servidor, ya que en su estado original el sistema operaba sobre canales no cifrados, carecía de controles de acceso y dependía de bibliotecas de código abierto desactualizadas. En consecuencia, los requisitos de software se centraron en implementar un mecanismo criptográfico de verificación mediante sumas de comprobación, migrar el servicio hacia el protocolo HTTPS mediante certificados digitales y auditar el código base para eliminar vulnerabilidades sin afectar la funcionalidad del negocio.

## Decisiones en la identificación de vulnerabilidades e importancia del código seguro

Para identificar las debilidades en el software de Artemis Financial, se tomó la decisión de combinar una inspección manual exhaustiva del código fuente con pruebas estáticas automatizadas a través de OWASP Dependency-Check. Esta estrategia dual resultó muy acertada porque me permitió detectar problemas que una herramienta automática por sí sola habría pasado por alto, tales como credenciales de base de datos incrustadas en texto plano en `DocData.java`, la ruptura de encapsulación en el campo `account_balance` de la clase `customer` y el uso de `printStackTrace()` que exponía trazas internas del servidor. A la par, en la etapa de refactorización decidí utilizar algoritmos estándar respaldados por el NIST, específicamente SHA-256 mediante `java.security.MessageDigest` para las sumas de comprobación y RSA de 2048 bits en un almacén PKCS12 para el canal TLS, descartando funciones obsoletas como MD5 o SHA-1 que ya presentan colisiones demostradas.

Desarrollar código seguro desde el inicio es fundamental porque previene que fallos de diseño o implementación se conviertan en puertas de entrada para ataques de inyección, interceptación de tráfico o robo de información. En el desempeño general de una organización financiera como Artemis Financial, la seguridad del software aporta un valor directo a la continuidad operativa y a la confianza del cliente. Un código robusto reduce drásticamente el riesgo de sufrir filtraciones de datos, evita costosas sanciones derivadas del incumplimiento de normativas como GLBA, PCI-DSS o GDPR, y protege la reputación corporativa. Además, detectar y corregir vulnerabilidades durante la fase de desarrollo resulta mucho más económico y eficiente que intentar remediar una brecha de seguridad cuando la aplicación ya se encuentra en producción.

## Retos y aprendizajes en el proceso de evaluación de vulnerabilidades

La parte más desafiante del proceso de evaluación de vulnerabilidades se presentó al ejecutar las pruebas estáticas con el complemento OWASP Dependency-Check que venía configurado originalmente en el archivo `pom.xml`. La versión 5.3.0 del plugin fallaba de manera continua porque intentaba conectarse a los antiguos feeds de datos NVD 1.1, los cuales fueron retirados por el NIST. Resolver este obstáculo me obligó a investigar el funcionamiento interno de la herramienta, actualizar el complemento a la versión 12.2.2 y configurarlo para consultar la nueva estructura de la base de datos NVD 2.0, logrando así un análisis completo sin errores de ejecución.

Por otro lado, la parte más útil fue contrastar los hallazgos del informe automatizado con la revisión manual línea por línea guiada por el diagrama de flujo de evaluación de vulnerabilidades. El reporte de Dependency-Check fue sumamente valioso para visibilizar más de doscientas vulnerabilidades ocultas en dependencias transitivas como Spring Boot 2.2.4, Tomcat 9.0.30, Jackson y SnakeYAML, incluyendo fallos críticos como Spring4Shell y Ghostcat. Sin embargo, la revisión manual me enseñó a leer el código con mentalidad defensiva y a comprender cómo pequeños descuidos en la validación de entradas o en la configuración de propiedades abren riesgos reales para la lógica del negocio.

## Reforzamiento de las capas de seguridad y recursos para evaluaciones futuras

Para reforzar las capas de seguridad apliqué un enfoque de defensa en profundidad enfocado en la integridad, la confidencialidad y la reducción de la superficie de ataque. En primer lugar, implementé el endpoint `/hash` utilizando el algoritmo SHA-256 con codificación explícita en UTF-8 para generar una suma de comprobación determinista que permitiera verificar que los datos no hubieran sido alterados. En segundo lugar, generé un par de claves RSA de 2048 bits y un certificado autofirmado mediante Java Keytool, los almacené en un contenedor `keystore.p12` y reconfiguré `application.properties` para forzar el tráfico exclusivamente a través de HTTPS en el puerto 8443. Finalmente, me aseguré de que el nuevo código utilizara constantes inmutables, manejara las excepciones mediante `IllegalStateException` sin filtrar detalles sensibles al usuario y prescindiera de bibliotecas externas innecesarias.

De cara al futuro, para evaluar vulnerabilidades y seleccionar las técnicas de mitigación más adecuadas emplearía de forma sistemática la Base de Datos Nacional de Vulnerabilidades (NVD) del NIST, el catálogo de vulnerabilidades explotadas conocidas (KEV) de CISA y las guías de buenas prácticas de OWASP, como el OWASP Top 10 y la serie de Cheat Sheets. Asimismo, apoyarme en los boletines de seguridad oficiales de los proveedores, como los avisos de Apache y VMware Spring, junto con los estándares criptográficos FIPS, me permitirá elegir controles actualizados y alineados con las exigencias de la industria.

## Verificación de funcionalidad, seguridad y control de regresiones

La comprobación de que el código refactorizado y la aplicación siguieran siendo tanto funcionales como seguros se realizó de manera incremental en cada capa implementada. Primero verifiqué que el proyecto compilara limpiamente y que el servidor Tomcat embebido arrancara sin errores escuchando peticiones HTTPS en el puerto 8443. Después accedí al endpoint `https://localhost:8443/hash` desde el navegador web y mediante `curl` para confirmar que la conexión TLS operaba correctamente y devolvía el resumen criptográfico esperado. Para no confiar ciegamente en mi propio código, validé la integridad del resultado calculando el hash de la misma cadena de texto con la utilidad externa `sha256sum`, comprobando que ambos valores coincidieran de forma exacta.

Posteriormente, para verificar que mis cambios no hubieran introducido nuevas vulnerabilidades, volví a ejecutar el análisis estático con `./mvnw dependency-check:check` sobre el proyecto refactorizado y comparé el informe resultante con la línea base inicial. El reporte analizó las 49 dependencias del proyecto y confirmó que la totalidad de las vulnerabilidades detectadas pertenecían a las librerías heredadas de la plantilla original, puesto que mi implementación se apoyó únicamente en paquetes nativos del JDK como `java.security.MessageDigest` y `java.nio.charset.StandardCharsets`. Sumado a una revisión manual de sintaxis, lógica y seguridad sobre el controlador modificado, esto garantizó que la refactorización estuviera libre de regresiones.

## Recursos, herramientas y prácticas de codificación útiles para el futuro

A lo largo de este proyecto utilicé un conjunto de herramientas y prácticas que serán de gran utilidad en mi desempeño profesional como desarrollador de software. En el apartado técnico, el manejo de Java Keytool para la gestión de almacenes PKCS12 y certificados X.509, el uso de las APIs criptográficas nativas de Java y la integración de OWASP Dependency-Check dentro del ciclo de construcción de Maven son habilidades directamente transferibles a entornos empresariales con pipelines de integración continua (CI/CD). Asimismo, el uso de utilidades de línea de comandos como `curl` y `sha256sum` me permitió realizar pruebas rápidas e independientes sobre los servicios web.

En cuanto a las prácticas de codificación, me llevo el hábito de aplicar configuraciones seguras por defecto, mantener una superficie de ataque mínima evitando dependencias superfluas, declarar estructuras inmutables cuando los datos no deben cambiar y especificar siempre la codificación de caracteres para evitar comportamientos inconsistentes entre sistemas operativos. También reforcé la importancia de un manejo de excepciones silencioso hacia el exterior y la necesidad de externalizar secretos, como las contraseñas del almacén de claves o de las bases de datos, mediante variables de entorno en lugar de dejarlos expuestos en archivos de configuración.

## Evidencia de competencias para futuros empleadores

Con base en el trabajo realizado para Artemis Financial, puedo presentar a futuros empleadores un portafolio sólido que demuestra tanto criterio analítico como capacidad de ejecución técnica en seguridad de software. Como primera evidencia cuento con el informe de evaluación de vulnerabilidades y el plan de mitigación priorizado, los cuales reflejan mi habilidad para auditar una API RESTful, identificar riesgos críticos en el código fuente, interpretar reportes de CVE y proponer soluciones alineadas con las necesidades del negocio y el cumplimiento normativo.

Como segunda evidencia puedo mostrar el código refactorizado en Spring Boot junto con el informe de prácticas de software seguro, donde se documenta paso a paso la implementación de SHA-256, la generación del certificado autofirmado RSA de 2048 bits, la configuración del canal HTTPS en el puerto 8443 y la validación sin errores mediante Dependency-Check. Estos artefactos comprueban de forma práctica que sé transformar requisitos de seguridad en código funcional, aplicar estándares criptográficos vigentes y verificar que una aplicación empresarial opere de manera confiable y protegida frente a amenazas reales.
